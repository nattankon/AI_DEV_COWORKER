# Cowork Project State

Last updated: 2026-08-23

## Core Product Architecture Decision

AI Dev Coworker is now defined as a three-mode local-first AI workspace. These modes must remain separate in memory, tools, prompt behavior, token strategy, and permission boundaries:

1. **Chat = ChatGPT/Gemini-like assistant**
   - Primary purpose: general conversation, learning, explanation, research, brainstorming, and chat-based code generation.
   - It must not directly mutate local files or run shell commands.
   - It must not automatically read the local workspace or project files. Workspace/project inspection belongs to Cowork or Code.
   - It may use controlled connectors such as web search, MCP connectors, user-uploaded files, explicitly attached context, and artifacts.
   - It owns Chat-specific personal memory for user preferences, answer style, and broad non-project goals.
   - It should remember broad user preferences such as language, answer style, and long-term goals, while avoiding stale project facts unless the user explicitly attaches context in Chat.
   - It should support low/medium/high effort as different reasoning and retrieval budgets, not merely as a UI label.
   - It should answer from model knowledge for ordinary questions, use web or connector search for current/external knowledge, and ask the user to attach files or hand off to Cowork when workspace evidence is required.
   - It should be allowed to become a conversational connector surface: the user can explicitly ask Chat to test or use a named MCP integration such as a Roblox MCP connection. Chat should report when no matching connector is available instead of pretending to connect. Future always-on connector discovery should be plugin-backed and user-visible, not silent broad scanning.
   - Chat code execution must prefer the Pyodide/WASM sandbox. Legacy subprocess execution is blocked unless an MCP client is actually connected and the user explicitly enabled the legacy sandbox path; even then it remains approval-gated and labeled experimental.

2. **Cowork = Codex-like workspace agent**
   - Primary purpose: complete project work inside a selected workspace.
   - It can inspect files, propose edits, request approval, write files, run allowlisted verification, manage rollback backups, and record audit events.
   - It owns Cowork/task memory tied to the active workspace and work logs, not ordinary personal chat memory.
   - It remains approval-gated for writes, verification, and restore operations.
   - It should optimize for task completion, evidence, tests, rollback, and progress reporting.

3. **Code = Claude Code-like coding interface**
   - Primary purpose: focused repository coding sessions, code understanding, diff review, and developer workflows.
   - It should evolve toward a denser code-first interface with repository maps, diagnostics, edits, staged changes, and test feedback.
   - It owns repo/coding-session memory separate from Chat and Cowork.
   - It may share some Cowork safety primitives, but its UI and working model should be optimized for interactive coding rather than general project management.

### Memory Boundary Decision

- `Chat` ordinary memory: user preferences, conversational style, broad goals, and non-project personal context.
- `Chat` attached context: files, snippets, artifacts, or MCP/web results explicitly selected for a Chat conversation. This is not automatic workspace reading.
- `Cowork` memory: workspace/task state, approvals, implementation evidence, work logs, and verification history.
- `Code` memory: repository structure, coding preferences, diagnostics, code review state, and implementation context.
- Memory from one mode must not silently bleed into another mode. Shared information must be promoted deliberately through a named summary or project record.

### Chat Knowledge Routing Decision

Chat must use an intent router before adding context:

- `general`: answer from the selected model and personal Chat memory; do not read project files by default.
- `project`: do not read workspace files automatically. Ask the user to attach files/context in Chat, or suggest switching/handing off to Cowork for workspace inspection.
- `web`: use web/search connectors for current or external facts, preferably official sources for technical/provider information.
- `memory`: use personal Chat memory or project Chat memory, with timestamps and uncertainty when needed.
- `mixed`: combine only the necessary sources and clearly separate project facts, general explanation, and suggestions.

The rule is: retrieve only what is relevant and only through Chat-appropriate sources. Do not stuff project files into Chat prompts, and do not let Chat silently inspect the workspace.

### Effort Routing Decision

- `Low`: lightweight generation and tool/retrieval budgets, with no retrieval unless the user explicitly asks or the answer clearly requires current facts. Conversation continuity is still fitted to the selected model's context window rather than discarded.
- `Medium`: route the question, retrieve targeted context when the classifier detects project/current/memory needs, and answer with concise evidence. Conversation continuity uses the same context-window planner as every effort level.
- `High`: route the question, use broader retrieval, compare sources, state uncertainty, and separate facts from assumptions and suggestions. It may reserve more output/tool budget but does not get a different memory-retention policy.

Effort controls reasoning, generation, retrieval, source, and tool-loop budgets. It must not silently delete recent conversation history; the selected model's real context window is the continuity boundary.

### Web Chat Bridge Decision

- `Web Chat` is an isolated browser surface, not a fourth native assistant mode. `Chat`, `Cowork`, and `Code` retain their existing sessions, memory, model routing, and permissions.
- Electron hosts the real ChatGPT website in a sandboxed `WebContentsView` using the persistent `persist:web-chat` partition. The user signs in on the real page, and that Chromium partition owns the resulting website session.
- The app does not expose a preload bridge to the remote page, enable Node integration, read cookies, extract OAuth tokens, or reuse the website session as an API credential.
- Native Chat/Cowork/Code history is hidden while Web Chat is active. Switching back restores the prior native mode without creating or mutating a native session.
- Phase 1 provides the isolated website surface, bounded navigation controls, lifecycle handling, and persistent login partition. Phase 2 adds an independently persisted, explicitly revocable grant for exactly one registered workspace and one requested permission profile.
- Phase 3 adds an internal local MCP gateway bound to the canonical grant ID, revision, and workspace path. Its built-in catalog exposes only `list_directory`, `search_files`, and `read_file`; optional provider tools must carry trusted read-only and workspace-bound annotations. Calls reuse workspace containment and Secret Guard, validate the current grant generation on every dispatch, and emit metadata-only audit records. The remote website still receives no IPC or tools because the authenticated tunnel remains Phase 4.
- Phase 4 adds an explicitly started authenticated tunnel around that local gateway. Electron main creates a fresh 256-bit bearer credential and passes it directly to the Python sidecar; it remains transient in those trusted processes and never enters renderer or website state. Renderer state contains only the provider, HTTPS endpoint, authentication-required flag, expiry, tool count, and lifecycle error. Tunnel state is enabled only for the exact active grant generation and canonical workspace. Disconnect, grant changes, one-hour credential expiry, fifteen-minute idle timeout, sidecar shutdown, and app exit close the listener and adapter process tree. Cloudflare Quick Tunnel is the first optional adapter; connector registration remains Phase 5.
- Phase 5 adds an explicit connector verification and registration handoff. Electron main probes the exact active public endpoint with bounded MCP `initialize` and `tools/list` requests before setup controls unlock. Only redacted server/protocol/tool-count metadata reaches React. Endpoint and bearer credential copy are separate user actions performed directly by Electron; IPC never returns the bearer, and an unchanged copied credential is cleared from the clipboard after 60 seconds. The embedded ChatGPT page is not inspected, automated, or given a preload bridge.
- Phase 6 expands the authenticated gateway to the complete bounded `WorkspaceTools` catalog: six read-only inspection tools plus approval-gated write, edit, backup restore, and allowlisted verification. Workspace-bound provider side effects use the same approval path. Remote side effects require the exact active tunnel generation before and after approval; tunnel teardown and grant replacement/revoke cancel pending approvals, while stale decisions fail closed. Approval cards show the complete arguments, generated diff or exact verification command, workspace/grant identity, and tunnel generation. The website surface is hidden while the native approval prompt is visible. Existing containment, Secret Guard, fixed verification presets, atomic writes, rollback, audit, and Manual/Trusted/Full permission profiles remain enforced.

## Current Capability

- Native Chat, Cowork, and Code session history is dual-persisted. Chromium localStorage remains the fast cache, while Electron atomically writes the same versioned envelope to `session-history.json` under the stable app `userData` directory and keeps `session-history.json.bak` as a recovery copy. Startup reconciles valid copies by `savedAt` and blocks all persistence until durable hydration completes, preventing a missing, corrupt, or temporarily unavailable renderer cache from silently replacing newer history with an empty state. This protection begins with the first run of the updated build; historical sessions that were already lost are intentionally not reconstructed.
- Standalone `cowork` CLI installs from `pyproject.toml` and runs from directories outside the source checkout.
- Local-first Cowork agent connected to LM Studio through an OpenAI-compatible API.
- Primary local model: `qwen/qwen3.5-9b`, Q4_K_M.
- Validated live text generation and structured `list_directory` tool calling through the standalone agent loop.
- Cowork-owned `WorkspaceTools` provides list, search, read, and approved atomic write operations.
- Canonical path validation rejects traversal and absolute targets outside the selected workspace.
- `SecretGuard` hides and denies high-confidence secret paths across list, search, read, and write operations.
- Blocked classes include `.env` variants, private-key/certificate files, SSH key names, credential files, and `.ssh`/`.aws`/`.azure`/`.gnupg`/`.kube` stores; explicit `.env` templates remain accessible.
- File writes display a unified diff and require approval unless the process is explicitly started with `--yes`.
- Workspace memory discovery is read-only; memory creation and updates must pass through approved `write_file` calls.
- The standalone Python runtime and npm package configuration contain no legacy host runtime references.
- CLI sessions and tool events are stored as append-only JSONL records.
- Agent loop performs one bounded recovery attempt when a Local AI model returns an empty response after tool use.
- Cowork-owned `DeveloperTools` provides read-only `git_status` and `git_diff` tools. Secret paths are filtered from Git status and diff output before results reach the model.
- Verification execution is allowlist-based through `run_verification`; current presets are `python-tests`, `frontend-tests`, and `frontend-build`.
- Verification presets require explicit command approval in the CLI unless the process is started with `--yes`; arbitrary shell command strings and model-supplied arguments are not accepted.
- Approved replacements now retain rollback backups under `.cowork/backups/<timestamp>/...` and return `backup_path` in the write result.
- Rollback backups can be restored with the approval-gated `restore_backup` tool. The target path is inferred from `.cowork/backups/<timestamp>/...`, and the current file is backed up before restoration.
- Rollback backups can be discovered with `list_backups`, which returns metadata only (`backup_path`, target path, byte count, modified time) and hides secret-classified targets.
- Workspace writes and verification runs emit structured audit events for approval requests, approval decisions, backup creation, file writes, verification starts, finishes, denials, and timeouts without storing full file contents in those audit payloads.
- Verification timeouts now use process-tree cleanup: Windows uses `taskkill /T /F`, while POSIX starts a new session and terminates the process group.
- Process-tree cleanup is covered by deterministic real worker-tree tests for both a Python parent/child tree and an `npm run` Node worker tree.
- `AgentRunState` adds an explicit Inspect -> Plan -> Act -> Verify -> Report flow around the agent loop.
- After a successful `write_file`, Cowork blocks final reporting until a passing `run_verification` result has been observed, then records structured completion evidence.
- `AgentRunState` can serialize to and restore from JSON-safe snapshots; `CoworkAgent.run()` accepts restored state and records `agent_state_snapshot` events so interrupted runs can resume through the same completion gate.
- `ipc_sidecar.py` is the Cowork-owned JSONL adapter for Electron. It runs Cowork requests on background workers so stdin remains available, emits renderer events on stdout, lists Local AI models, and pauses write/verification operations until a matching UI approval response arrives.
- Sidecar worker failures are converted into structured `backend-log` events instead of escaping silently from a background thread.
